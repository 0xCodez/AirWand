# Contributing to Orbit

Thanks for helping. Orbit is two programs that must agree byte for byte: the phone app in `mobile/` and the desktop agent in `desktop/`. Most of the rules below exist to keep them in sync.

## Ground rules

- Be kind. Assume good intent.
- Open an issue before large changes, so we can agree on the approach first.
- Security problems go to [SECURITY.md](SECURITY.md), never to public issues.

## Development setup

### Desktop agent (`desktop/`)

| | macOS | Windows |
|---|---|---|
| Toolchain | Rust stable via [rustup](https://rustup.rs) | Rust stable via rustup (`x86_64-pc-windows-msvc`) |
| System | Xcode Command Line Tools (`xcode-select --install`) | Visual Studio Build Tools, workload "Desktop development with C++" |
| Permission | Grant **Accessibility** to your terminal (when running `cargo run`) or to `Orbit.app` | Allow TCP+UDP 47821 (`desktop/scripts/firewall-windows.ps1`, run as Administrator) |

```bash
cd desktop
cargo fmt
cargo clippy --all-targets
cargo test
cargo run --release
```

macOS universal bundle:

```bash
rustup target add aarch64-apple-darwin x86_64-apple-darwin
bash scripts/bundle-macos.sh      # -> desktop/dist/Orbit.app (ad-hoc signed)
```

Tip: macOS ties the Accessibility grant to the binary's signature. After rebuilding the bundle you may have to remove Orbit from *Privacy & Security → Accessibility* and add it again.

Linux is not a supported host in v0.1 (see [docs/ROADMAP.md](docs/ROADMAP.md)), and CI does not build on Linux.

### Phone app (`mobile/`)

Requirements: Flutter **stable**, Java 17 + Android SDK for Android, Xcode + CocoaPods for iOS.

The `android/` and `ios/` platform folders are **not committed**. They are generated by the bootstrap script, which also applies the project-specific platform settings (such as permissions and Info.plist keys):

```bash
cd mobile
bash tool/bootstrap.sh            # on Windows run it from Git Bash
flutter pub get
flutter analyze
flutter test
flutter run
```

If you need a platform-level change (a manifest permission, an Info.plist key), change `tool/bootstrap.sh`, not the generated folder, or it will be lost on the next bootstrap and in CI.

### Testing end to end

Put the phone and the computer on the same network. Run the agent from source, run the app on a real phone (simulators and emulators usually cannot see the host's mDNS or reach it over UDP reliably), pair, and exercise every mode you touched. The interactive UI prototype in `docs/prototype/index.html` is handy for checking visual changes against [docs/DESIGN.md](docs/DESIGN.md).

## The protocol change rule

[`docs/PROTOCOL.md`](docs/PROTOCOL.md) is the single source of truth for the wire format. Any change to discovery, pairing, packet layout, message types, payloads, ports or crypto **must**:

1. Update `docs/PROTOCOL.md` first, in the same PR.
2. Implement the change on **both** sides (`desktop/` and `mobile/`) in that same PR. A PR that changes only one side of the wire will not be merged.
3. Bump the protocol version `v` (and the header version byte) if an old peer would misbehave. Additive changes that old peers safely ignore, such as a new optional JSON field, do not need a bump, but say so in the PR.
4. Add or update tests on both sides that pin the exact bytes (for example, a known plaintext encoded to a known packet layout, or the HKDF code derivation with fixed inputs).

Use the `protocol` commit scope for these changes.

## Design changes

UI work follows [docs/DESIGN.md](docs/DESIGN.md): its tokens, radii, springs, haptics and the reduce-motion rules. If you need a new token or pattern, add it to `DESIGN.md` in the same PR.

## Commit style

[Conventional Commits](https://www.conventionalcommits.org):

```
<type>(<scope>): <summary in imperative mood, lower case, no period>
```

- **types:** `feat`, `fix`, `perf`, `refactor`, `docs`, `test`, `build`, `ci`, `chore`
- **scopes:** `desktop`, `mobile`, `protocol`, `design`, `docs`, `ci`, `repo`
- Breaking changes: add `!` after the scope and a `BREAKING CHANGE:` footer.

Examples:

```
feat(mobile): three-finger swipe switches the active computer
fix(desktop): release held buttons when a device goes quiet
feat(protocol)!: add host-issued session challenge
ci: cache the Flutter SDK on macOS runners
```

Keep commits focused; squash fix-ups before review. Pull requests are squash-merged, so the PR title must follow the same format.

## Pull requests

- Fill in the PR template, including how you tested it (devices and OS versions).
- CI must be green. In v0.1 `cargo fmt --check` and `cargo clippy` are reported but non-blocking; `cargo test`, the release builds, `flutter analyze` and `flutter test` are blocking.
- Attach screenshots or a short screen recording for anything visible.

## CI and releasing

There are two workflows, each triggered only by changes in its own folder:

| Workflow | Runs on | Produces |
|---|---|---|
| `.github/workflows/desktop.yml` | `macos-latest`, `windows-latest` | `Orbit-macos-universal.zip`, `orbit-windows-x64.exe`, `firewall-windows.ps1` |
| `.github/workflows/mobile.yml` | `ubuntu-latest` (Android), `macos-latest` (iOS) | `orbit-android.apk`, `orbit-ios-unsigned.ipa` |

Builds of every push and PR are available as workflow artifacts for 30 days.

### Releasing

There is deliberately **no separate `release.yml`**. Sharing build jobs through `workflow_call` would add complexity for little gain, so each workflow has its own final `release` job that runs **only on tag refs** (`refs/tags/v*`). It downloads that workflow's artifacts and attaches them to the GitHub Release for the tag with `softprops/action-gh-release@v2` (it needs `contents: write`, granted to that job only).

To cut a release:

1. Update versions (`desktop/Cargo.toml`, `mobile/pubspec.yaml`) and merge to `main`.
2. Tag and push:
   ```bash
   git tag v0.1.0
   git push origin v0.1.0
   ```
3. Both workflows run on the tag (path filters do not apply to tag pushes) and attach their files to the same release. The first one to finish creates the release; the second adds to it.
4. Edit the generated release notes if needed.

Notes:

- Rarely, if both workflows finish at the same moment, two releases for the same tag can be created. Delete the empty one and re-run the failed `release` job.
- v0.1 Android APKs are signed with the Flutter debug key, and the iOS IPA is unsigned. Store signing is on the roadmap.
